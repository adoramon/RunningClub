# 东成西就项目记录

> 本文件是本项目的持续上下文。每次开始新的开发回合前，先阅读本文件、`README.md` 与相关代码；每完成一个可验证阶段，更新本文件并随代码提交。

最后更新：2026-08-05

## 1. 项目目标

为封闭跑团“东成西就”建设原生微信小程序，长期保存既有历史记录，并提供：成员身份认领、月度承诺、运动凭证上传、公积金结算与历史分析。

## 2. 已确认的业务规则

- 成员按月承诺跑量；首次未完成和连续未完成分别按缺口 `3 / 6 / 9 ... 元/公里` 缴纳公积金。
- 任意一个月完成承诺，连续未完成次数清零；下次未完成重新按 `3 元/公里` 计算。
- 所有罚金统一称为“公积金”。截至 `2026-07` 的历史结转余额为 `-257.00` 元（亏空），后续从该值持续累计。
- 换算：自行车距离 ÷ 3；游泳距离 × 5；跳绳个数 ÷ 100；爬升米数 × 0.02，均得到跑步等效公里数。其他运动需管理员确认。
- 历史数据不可覆盖或丢弃：原始单元格值、来源表与坐标都应可追溯。
- 历史汇总按月计算：仅纳入该月“承诺跑量”有数值的成员。承诺为空表示当月尚未加入跑团，必须从当月人数、承诺总量、实际跑量总量和榜单中排除；不能按全体 27 人固定统计。
- 当月承诺跑量和实际跑量均为空时，标记为 `historical_inactive`（历史人员，未参与当月统计）：团队汇总不计入，但个人历史页保留并明确展示该状态。实际有值但承诺为空的原始异常记录也仅作历史展示，不计入完成率。
- 历史“收/交 XX 元”均为公积金罚金：保留原始文本与金额，并根据该成员截至当月的连续未达标次数倒算当月跑量：`实际跑量 = 承诺跑量 - 公积金 ÷ (3 × 连续未达标次数)`。全额罚金因此倒算为 0 km；倒算跑量计入团队和个人历史统计，并标记为“按公积金倒算”。遇到没有承诺或倒算结果越界的记录必须标记待核验，不得伪造。

完整模型见 [domain-model.md](domain-model.md)。

## 4. 已部署云函数

- `get_current_user`：以 OpenID 创建或读取最小用户记录。
- `suggest_historical_aliases`：按昵称提供历史艺名模糊匹配建议。
- `claim_historical_identity`：精确验证并原子认领一个未被占用的历史艺名。
- `save_profile_avatar`：保存云存储头像 File ID。
- `get_historical_dashboard`：只读返回上一个完整月的团队历史汇总、有效成员明细，以及当前认领成员的历史分析与自动继承承诺。
- `import_legacy_history`：历史导入期间使用；历史数据已改由控制台 JSON 导入完成。

> 不要部署或恢复 `update_profile`：它属于旧的自由昵称演示流程，违背封闭跑团准入规则。

## 5. 身份认领流程（当前实现）

1. 启动时调用 `get_current_user`；未认领历史身份的用户被带到注册页。
2. 用户填写微信昵称，选择微信头像。
3. 前端调用 `suggest_historical_aliases` 显示建议；用户必须最终确认一个历史艺名。
4. `claim_historical_identity` 仅允许匹配存在且未认领的艺名；成功后绑定 OpenID 与历史成员记录。
5. 已认领用户才可以进入跑团看板及后续功能。

## 6. 关键坑与处理结论

### 微信昵称不能用旧式授权弹窗强制读取

- 曾尝试点击按钮调用 `wx.getUserProfile`。开发者工具中不会可靠地弹出昵称授权，且该接口不应作为当前昵称获取的稳定方案。
- 当前采用微信组件的 `input type="nickname"`（基础库 2.21.2 起支持），点击输入框会调起昵称输入键盘并协助填写。
- 微信平台不允许小程序静默、强制读取用户真实昵称。因此产品文案不得承诺“自动读取”；昵称与头像可以设为必填，但昵称仍需用户在微信界面确认/填写。
- 头像使用 `button open-type="chooseAvatar"`；样式已修复为固定圆形，避免微信 button 默认尺寸导致椭圆。

### 云函数部署与三秒测试限制

- 控制台“运行测试”有 3 秒限制，不适合执行大量历史数据逐条写入；历史数据已改用控制台 JSON 导入，避免超时和重复写入风险。
- 云函数已部署。未来多个函数一起发布时，使用微信开发者工具原生 CLI 的 `cloud functions deploy --paths` 一次部署；不要逐个使用包装 Skill，以减少重复确认。
- 微信开发者工具已开启服务端口并授权 Codex CLI。CLI 操作仍可能受开发者工具的安全确认机制控制，这是工具侧权限边界。

### 首页未跳转到认领页

- 开发者工具热刷新有时不会重新触发完整页面生命周期。用“重新编译”或直接打开 `pages/register/register` 验证；真实的未认领用户会被首页逻辑重定向。

当前阶段：封闭成员身份认领已完成，并已在开发者工具中完成一次完整认领链路测试（昵称、头像、艺名匹配和唯一绑定均通过）。

本阶段已完成：历史真实数据已接入首页和分析页。首页不再使用演示成员或实时“本月进度”，而是展示上一个完整月的真实团队汇总与榜单；仅统计当月有承诺的成员。认领成员的本月承诺从该成员当前月或最近一次有值的历史承诺自动继承。

看板展示规则：看板统一展示上一个完整月的数据。上月团队卡片只显示“有承诺人数、已提交人数、实际跑量和承诺跑量”，并使用达成率圆环；不展示额外百分比文字。公积金卡片显示当前余额与上月新增公积金：历史月份优先汇总历史记录中的“收/交 XX 元”罚金，正式结算上线后由确认流水提供数值；余额以 `-257.00` 元历史结转为基数、后续以确认流水累计。上月未提交的认领用户显示醒目的提交引导。上月排名按达成率而非公里数排序；达成率相同时，按上月实际跑量从高到低排序。使用上月有承诺成员：已认领成员展示微信昵称和头像，未认领成员展示历史艺名及灰色“未注册”标记。圆环展示实际整数百分比（允许超过 100%），按 >120 深绿、100–120 浅绿、80–100 深黄、50–80 浅黄、10–50 红、<10 深红区分。未达成但已缴公积金显示绿色“已缴纳公积金”；未缴显示红色“请尽快缴纳公积金”；未记录跑量显示红色“请尽快提交跑量数据”。

首页将“一起把承诺跑成日常”马拉松主视觉、上月团队完成情况和累计统计融合为一张连续的跑团战报卡：主视觉向下以深绿渐变过渡到结算区，不再保留两张独立卡片间的空隙。结算区使用放大的高对比浅绿色达成率圆环，不再使用横向进度条；放大的“上月团队完成情况”标题与“XX 人已承诺 · XX 人已提交”同行展示。上月全员实际跑量与全员总承诺跑量在同一对比区等宽、等字号并列展示：左侧数据右对齐、右侧数据左对齐，并给两侧相同的内边距，使两组数字内侧边界到中央半透明竖线的留白保持一致；不为承诺跑量额外使用独立背景框。卡片下部为浅色趣味统计区：布局不变，但累计里程、运营时长与四项对比的文字和数值均使用更淡的低强调色，避免喧宾夺主。累计公里数与根据最早有效承诺月计算的跑团运营时长同行显示，下方四项动态对比均以“相当于 + 项目 + 数值”的单行形式展示，进一步压缩高度；不展示有效记录条数或地月往返。累计统计全部历史有效月记录（含罚金倒算跑量），在后台单独读取，避免阻塞看板首屏；同一云函数实例缓存 30 分钟。

上月跑量排名的每一行均可点击（姓名、里程和完成率圆环均覆盖在同一个点击区域），跳转到独立的“成员个人分析”页。该页面接受历史成员 ID，并通过已认领成员才可调用的云函数读取该成员的艺名/已绑定昵称、头像、当前继承承诺、历史月均与最高跑量及历史台账；未注册成员仍仅展示艺名和默认头像。
