# 东成西就项目记录

> 本文件是本项目的持续上下文。每次开始新的开发回合前，先阅读本文件、`README.md` 与相关代码；每完成一个可验证阶段，更新本文件并随代码提交。

最后更新：2026-08-28

## 1. 项目目标

为封闭跑团“东成西就”建设原生微信小程序，长期保存既有历史记录，并提供：成员身份认领、月度承诺、运动凭证上传、公积金结算与历史分析。

## 2. 已确认的业务规则

- 成员按月承诺跑量；首次未完成和连续未完成分别按缺口 `3 / 6 / 9 ... 元/公里` 缴纳公积金。
- 任意一个月完成承诺，连续未完成次数清零；下次未完成重新按 `3 元/公里` 计算。
- 所有罚金统一称为“公积金”。截至 `2026-07` 的历史结转余额为 `-257.00` 元（亏空），后续从该值持续累计。
- 换算：自行车距离 ÷ 3；游泳距离 × 5；跳绳个数 ÷ 100；爬升米数 × 0.02，均得到跑步等效公里数。其他运动需管理员确认。
- 历史数据不可覆盖或丢弃：原始单元格值、来源表与坐标都应可追溯。
- 历史汇总按月计算：仅纳入该月“承诺跑量”有数值的成员。承诺为空表示当月尚未加入跑团，必须从当月人数、承诺总量、实际跑量总量和榜单中排除；不能按全体 27 人固定统计。
- 当月承诺跑量和实际跑量均为空时，标记为 `historical_inactive`（历史人员，未参与当月统计）：团队汇总不计入，但个人历史页保留并明确展示该状态。实际有值但承诺为空的原始异常记录也仅作历史展示，不计入完成率。
- 历史“收/交 XX 元”均为公积金罚金：保留原始文本与金额，并根据该成员截至当月的连续未达标次数倒算当月跑量：`实际跑量 = 承诺跑量 - 公积金 ÷ (3 × 连续未达标次数)`。全额罚金因此倒算为 0 km；倒算跑量计入团队和个人历史统计，并标记为“按公积金倒算”。遇到没有承诺或倒算结果越界的记录必须标记待核验，不得伪造。

完整模型见 [domain-model.md](domain-model.md)。

## 5. 身份认领流程（当前实现）

1. 启动时调用 `get_current_user`；未认领历史身份的用户被带到注册页。
2. 用户填写微信昵称，选择微信头像。
3. 前端调用 `suggest_historical_aliases` 显示建议；用户必须最终确认一个历史艺名。
4. `claim_historical_identity` 仅允许匹配存在且未认领的艺名；成功后绑定 OpenID 与历史成员记录。
5. 已认领用户才可以进入跑团看板及后续功能。

## 6. 关键坑与处理结论

### 微信昵称不能用旧式授权弹窗强制读取

- 曾尝试点击按钮调用 `wx.getUserProfile`。开发者工具中不会可靠地弹出昵称授权，且该接口不应作为当前昵称获取的稳定方案。
- 当前采用微信组件的 `input type="nickname"`（基础库 2.21.2 起支持），点击输入框会调起昵称输入键盘并协助填写。
- 微信平台不允许小程序静默、强制读取用户真实昵称。因此产品文案不得承诺“自动读取”；昵称与头像可以设为必填，但昵称仍需用户在微信界面确认/填写。
- 头像使用 `button open-type="chooseAvatar"`；样式已修复为固定圆形，避免微信 button 默认尺寸导致椭圆。

### 云函数部署与三秒测试限制

- 控制台“运行测试”有 3 秒限制，不适合执行大量历史数据逐条写入；历史数据已改用控制台 JSON 导入，避免超时和重复写入风险。
- 云函数已部署。未来多个函数一起发布时，使用微信开发者工具原生 CLI 的 `cloud functions deploy --paths` 一次部署；不要逐个使用包装 Skill，以减少重复确认。
- 微信开发者工具已开启服务端口并授权 Codex CLI。CLI 操作仍可能受开发者工具的安全确认机制控制，这是工具侧权限边界。

### 首页未跳转到认领页

- 开发者工具热刷新有时不会重新触发完整页面生命周期。用“重新编译”或直接打开 `pages/register/register` 验证；真实的未认领用户会被首页逻辑重定向。

管理员审核设定：仅历史艺名 `高翔`（`legacy-member-023`）和 `元`（`legacy-member-001`）对应的已认领微信账号可读取或操作审核队列，权限由云函数按 `historicalMemberId` 校验，不依赖可变微信昵称。成员确认后进入 `pending_admin_review`；管理员首页显示待审核数量与入口。管理员可点击凭证查看原始截图、逐项校正原始数值或取消计入；服务端按锁定的运动类型和单位重算，保存 `adminReviewedActivities` 与 `adminApprovedEquivalentKm` 作为最终核定数据。任一管理员点击通过后记录立即设为 `approved` 并写入审核人、审核时间，另一位管理员无需重复操作。管理员可填写成员可见的原因并将不合格提交设为 `voided`；原始图片及识别结果保留审计，成员可重新提交。审核后正式月度结算仍待后续开发。

管理员“上月未提交”管理：审核页额外列出上一个完整月中有承诺、没有实际跑量、没有历史公积金且没有有效截图提交的成员。金额由云函数读取该成员此前历史记录，按连续未达标次数计算 `承诺缺口 × 3 元 × 连续未达标月数`；前端不可传入或改写金额。管理员可将该月设为“提前请假”（不生成公积金流水），或确认“已缴公积金”。确认缴纳会原子写入 `monthly_settlements` 与 `fund_ledger/member_payment`，后者状态为 `confirmed`，因此立即计入跑团公积金当前余额和上月新增公积金。该操作针对上月；本月请假登记另行设计，避免与上月结算混淆。

公积金收支公示：主页余额区可进入 `pages/fund-ledger/fund-ledger`，所有已认领成员可查看状态为 `confirmed` 的 `fund_ledger` 流水、当前余额、累计缴入和累计支取。历史结转作为单独的“历史结转余额”行展示，不归入支取。仅管理员“高翔”（`legacy-member-023`）与“元”（`legacy-member-001`）可调用 `manage_fund_ledger/withdraw`；服务端在事务内复算确认流水余额，提取金额必须为正、不得大于可用余额、用途必须为 2 至 100 字。成功后写入 `admin_withdrawal` 负数流水、用途与经办人，任何成员随后可见；前端权限只影响显示，不能替代服务端校验。

历史总账迁移：原 Excel 的第 31 行为月度收入汇总，第 33/34 行为支取或调整及余额滚动。仅汇总两行会出现 `102.00` 元差额；该差额已作为 `2021-10` 的 `opening_balance +102.00` 元导入。收入总额 `15,437.00` 元，按余额公式实际扣减的历史支取/调整总额 `15,796.00` 元，三者合计恰为 `-257.00` 元。本地生成的受 `.gitignore` 保护的审计迁移文件为 `migration-data/legacy_fund_ledger_details.json`：53 条 `legacy_monthly_income`、8 条 `legacy_expense`、1 条期初余额，均保留工作表与原始单元格/公式来源；明细以云数据库为准，不将成员资金流水推送到公开代码仓库。原 `legacy-opening-2026-07` 最终结转行在详细导入后必须标记为 `superseded`，避免与已展开的历史流水重复计入。公示页只显示最近一个有流水月的明细，同时按年、每行四个月展示“收 / 支 / 余额”宫格；“管理员提取公积金”说明文案不展示具体管理员姓名，但云函数权限仍只允许两个既定管理员。

最近月明细展示规则：公示页不再把最近月仅显示为月度汇总行，而是逐笔列出流水。历史月度收入会优先用同月 `historical_monthly_records` 中的 `fundAmount` 核对汇总金额；两者一致时，逐笔显示为“缴纳公积金 / 艺名缴纳”，而非暴露“历史台账拆分项”的内部术语。若历史逐笔金额与月度总账不一致，则保留原始汇总流水以避免错配。月度收支宫格固定为更矮、更接近正方形的紧凑版“收 / 支 / 余额”布局。

公示金额与文案规则：所有金额经服务端格式化为带千分位的文本，保留至多两位小数。`member_payment` 流水主标题统一为“缴纳公积金”，副标题显示已关联的微信昵称（优先）或历史艺名加“缴纳”；不展示管理员确认人。负数支取/跑团支出则保留并展示其用途备注。月度宫格采用左侧“收 / 支 / 余额”标签、右侧大号金额的对齐布局。

未达标缴费提醒：上月截图经管理员通过后，系统以管理员核定等效跑量覆盖上月看板的实际跑量。若该值低于承诺，成员会进入管理员“待确认缴纳公积金”清单；列表显示实际/承诺、缺口、连续未达标次数、费率和应缴金额。通过审核后页面会弹窗询问管理员是否立即确认到账；取消不会生成流水，成员继续留在清单。成员本人登录首页时，若其上月存在未确认的跑量缺口，会看到“请尽快缴纳公积金”提示及服务端计算的应缴金额。管理员确认到账后才写入 `member_payment`，余额才增加。

阶段性运动评价：成员在上传页确认上月识别结果、提交至管理员审核后，前端异步调用一次 `generate_monthly_evaluation`。函数仅读取成员确认的等效跑量、上月承诺和近期历史跑量摘要，调用自建 OpenAI 兼容网关的 `local-premium` 文本模型，绝不发送截图或 API 密钥。结果保存到活动记录的 `memberEvaluation`，按 `revision` 与提交版本绑定；个人分析页仅读取该持久化结果，整月反复打开不会再次调用模型。评价模型的内部请求上限为 45 秒，以匹配函数的 60 秒运行时上限并预留数据库写入时间。为让已导入的 2026-07 历史数据默认可展示，管理员可逐成员触发受权限保护的历史回填：函数按既有公积金反推规则重建实际跑量，并将评价写入独立集合 `monthly_evaluations`，绝不创建或伪造截图提交。批量模型输出超过时限时按单成员回填，已对 19 名具备有效承诺与实际跑量依据的成员完成 2026-07 回填；所有已登录跑团成员均可在该成员的历史分析页看到历史回填评价，实时截图提交评价仍仅本人可见。个人页按来源显示“历史跑量数据”或“已确认提交数据”。重传确认会递增提交版本并生成新的评价。评价不影响管理员审核、公积金、排名和最终结算，仅在本人个人分析页“最近两年的跑量趋势”上方以阶段性激励卡展示。

2026-08-28 二次真实验证中，模型已正确返回游泳 `48806 m`，但界面出现 `244030 km`。根因是 `normalizeActivities` 调用换算函数时漏传 `rawUnit`，让距离换算默认当作 km；已修复为传入单位。该值应为 `48.806 km × 5 = 244.03 km`。任何显示为 244030 km 的旧识别记录均不可确认，须取消后重传。
